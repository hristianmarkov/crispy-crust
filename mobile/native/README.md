# Native companion implementation status

These sources have reproducible phone runner/target integration scripts, but **they are not claimed compiled, signed, physically tested or store-ready until CI and device evidence exist**. Core phone baking does not depend on a watch. Device compatibility must be named after testing.

- `apple/Package.swift` provides versioned task/action models and XCTest cases. Run `swift test` on macOS (also in CI).
- `scripts/embed_apple_targets.rb` adds watch and widget targets directly to generated Flutter Runner using pinned xcodeproj, source files/plists, target dependencies and Embed Watch/Plugins copy phases. macOS `bootstrap.sh` invokes it automatically. `apple/project.yml` is also available for standalone companion work; the main Flutter build uses the embedded targets. An explicit `enableLiveActivity` request starts/updates an activity through the phone bridge; watch commands are relayed to Dart and acknowledged only after the application repository accepts them. Owner-controlled team/signing and actual build/device validation are still required.
- `apple/Watch` receives snapshots through WatchConnectivity and sends acknowledgement commands. It never marks a physical bake action complete itself; phone-side revision and operation-id checks must accept the action before confirming.
- `wearos` is a native Wear OS Gradle application receiving `/crispy/task` Data Layer snapshots and sending `/crispy/action` acknowledgements. The bootstrap configuration includes it as the phone Gradle project's `:wear` module; run `./gradlew :wear:assembleDebug` from the generated phone `android` folder (also in CI). Same package name/signing identity as the phone is required for Data Layer connectivity. Phone-side Data Layer transport and acknowledgement relay are implemented; repository action validation and physical pairing tests remain required.

The phone platform adapters and deterministic tests are under `apps/mobile/lib/platform` and `apps/mobile/test/platform`. Native phone runners are generated reproducibly by `scripts/bootstrap.sh`, then configured by `scripts/configure_platforms.py`. That script installs the notification boot receivers, point-of-use permission declarations, exact auth callback, privacy descriptions, busy-time-only calendar bridge and keep-awake bridge. It does not register paid services or create store identities.

Permission denied, unsupported platform, stale sensor/watch data and missing cloud configuration are explicit states. Local notification delivery remains subject to OS permissions, Focus/DND, battery behaviour, device power and Android force-stop. No unattended background camera or universal probe/watch support is claimed.

Outstanding physical/owner gates: Apple/Google signing/accounts; named minimum/device matrix; notification denial/reboot/OEM tests; app-group/extension provisioning; BLE model/protocol verification; watch pairing/reconnect/stale/replay tests; production backend URL/publishable key; OAuth provider/sender/redirect setup. No production account keys belong in source.

## Provisional product identity

Phone Android applicationId, Wear OS applicationId and iOS Runner bundle ID are `app.crispycrust.mobile`. Apple companion bundle IDs are `.watch` and `.widgets` beneath that identifier. Android namespaces/Kotlin class packages remain `app.crispycrust.crispy_crust` for the phone and `app.crispycrust.wear` for Wear; manifests use full class names so applicationId changes cannot redirect components. Data Layer connectivity additionally requires matching phone/watch signing certificates. The identifiers are build defaults, not a claim of store registration; the owner must confirm them before enrolment/signing. The auth URL scheme remains `app.crispycrust` and is independent of package identity.
