## Shared project and deployment state

The owner explicitly authorised reusing the existing CrispyCrust Supabase project after the separate-project free quota was reached. App objects use `cc_`/`app_private`; the legacy waitlist tables and function are preserved. The app does not use the website API as its backend. This is an approved infrastructure exception, not a reduction of the product scope or a security-isolation guarantee.

The kernel and media/billing migrations were applied with remote versions `20261111151503` and `20261111151519`. The Vault-protected worker migration was applied as **`20261111155139`**, and its separate read-only health migration as **`20261111155946`**. Initial hosted checks verified RLS on the 19 public app tables and a private media bucket, with no new app security-advisor findings at that checkpoint. Re-run security checks after subsequent changes.

`app-api` version 2, `job-worker` version 2 and `revenuecat-webhook` version 1 have been deployed. RevenueCat/store configuration and the purchase lifecycle remain unverified. The named worker cron remains **inactive**. Automatic approval review rejected forced dispatch verification because that route can process queued jobs, including deletion; no activation or completed-erasure claim follows from deploying the function. The separate purpose-scoped read-only health route returned HTTP 200 with no job processing; the health capability was consumed and the queue remained empty. This does not authorise or verify job processing. Consult the backend's [deployment documentation](backend/README.md) for the current migration and worker state before any further action. Auth callbacks, provider availability and end-to-end account flows have not been established by these deployments.
